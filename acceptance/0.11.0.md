## Open at ship time

New, and known:

- ~~**This release's own tarball has not been run on macOS**~~ — **CLOSED after
  shipping, same day.** It was open at the tag and could not be otherwise: the
  artifact does not exist until it is published, which is true of every release
  at the moment of tagging. Once 0.11.0 was on npm it was installed globally on
  a `macos-latest` runner and invoked through the real bin symlink; see
  **Verified after shipping**. Left here rather than deleted, because what this
  record is for is saying what was known when the tag was pushed.
- **The npm deprecation notice on `<0.9.0` understates its own evidence.** It
  reads "Broken on Linux and macOS (verified on Linux)", written when macOS was
  inference. macOS has since been measured. The notice is conservative rather
  than wrong, and rewriting it needs a second `npm deprecate` run.
- **A permission-bit-only change under `copy` is not detected.** `chmod +x`
  with byte-identical contents is invisible, because changed files are compared
  by content hash and size. Documented in `docs/operations.md`. Detection alone
  would be worse than the gap: such a file would be reported as modified while
  contributing no patch section, which is the state `applyWorkspace` refuses —
  a silently dropped bit would become a refused apply.
- **A `model` naming no configured route is still routed leniently.** It is the
  OpenAI protocol's own field and clients fill it with placeholders; refusing
  it would break ordinary clients.
- **MCP-side `prompt` and `models` lengths are unbounded.** The HTTP surface is
  capped at `MAX_REQUEST_BODY_BYTES` (10 MB) with a clean 413; the MCP caller is
  local and uncapped. Deliberate — inventing a limit would be speculative.
- **Two prototype-chain sites were fixed without tests**
  (`http/server.ts`'s dispatcher filter, `mcp/config-hot-reload.ts`). Both take
  their names from config rather than a caller, so triggering them needs a route
  literally named `constructor` in `config.yaml`, and a test that cannot be
  shown failing against the old behaviour is not kept here.

Carried from 0.10.0, none re-verified for this release:

- MCP JSON-RPC error frames bypass the redaction sinks on the HTTP transport;
  covered on stdio by `installOutputRedaction`.
- `stream-subprocess` has no backpressure; past `maxBufferedChunks` the child is
  killed and the iterator rejects.
- Redaction is value-based, so an `api_key` that is an ordinary word mangles
  output wherever that word appears.
- `.supervisors/` still grows for non-empty spawn logs, deliberately.
- The Windows `workspace-resolve` git-spawn flake, roughly 1 full-suite run in
  11. Not diagnosed.
- 0.9.0's carried list, also not re-verified: breaker counts lost past ~24
  concurrent processes; `durationMs` excludes the response body read; a
  timeout-killed body read does not name the timeout; `fetch_benchmarks.py`
  cp1252 on Windows; a bare `HTTP/2 429`; the workspace marker file forgeable by
  a same-uid attacker; `apply`'s dirty-tree refusal exists only inside a git
  repo.

### Found on Linux

1. ~~**A route named as the OpenAI `model` is only honoured inside the best
   tier.**~~ **FIXED the same day, under `[Unreleased]`** — a named route now
   crosses tiers, and the fix was re-measured on the same Linux install:
   `model: "route_deep"` (tier 4) returns the tier-4 route's answer and its
   server logs the request. Measured with three stub routes: `model: "route_deep"` (tier 4)
   was answered by `route_cheap` (tier 3) — the named route was never called,
   and its stub logged no request. `model: "route_peer"` (same tier) did route
   correctly. The cause is that `modelMatchesService` adds `modelMatchBonus`
   to a score, and a bonus only reorders within a tier — the identical failure
   already documented and fixed for the `local` task-type bonus in
   `router.ts`. This lands hardest on the HTTP surface, because `/v1/models`
   advertises those route ids as models and `service` is refused there by name
   ("an explicit route choice was silently overridden by the router's pick"),
   so an HTTP client has no way to reach a route it can see listed.
   `routing.modelHintDropped: true` is reported, but no ordinary OpenAI client
   reads `harness_dispatch`.
2. **The zero-route config is the literal text `{}`.** On a machine with no
   harness CLI, `configure --print` prints `{}` and `configure --yes` writes a
   file whose body is `{}` under its explanatory header. "Detected 0 harness
   routes" is honest, but neither path says the one thing that would unblock
   the user — an `endpoints:` entry needs no CLI, which `doctor` does say.
3. **`--service <route>` prints a policy clause with no subject.** `routeTo`
   returns `policy.skipped.message` verbatim, and those messages are written
   to be prefixed by a route name ("route is disabled", "this is an HTTP model
   endpoint — …"). Printed alone by the CLI they read as fragments.
4. **A misleading error when an upstream ignores `stream: true`.** A stub that
   answered a streaming request with an ordinary JSON body produced `No answer
   in response body: {…"content":"pong"…}` — the message contradicts the body
   it quotes. Some OpenAI-compatible servers do ignore `stream`.
5. **A failed dispatch returns 502 with a success-shaped body.** Correct
   status, but the payload is a `chat.completion` with `content: ""` and
   `finish_reason: "stop"` and no top-level `error` object; the reason sits in
   `harness_dispatch.error`. A client that reads the body before the status
   sees an empty successful answer.

**All five are fixed, under `[Unreleased]`, and each was re-measured on the
same Linux install through the global bin symlink rather than in a test
alone:** the named route answers and its server logs the request; `configure`
with no harness prints and writes an explained file that still loads as an
empty config; `--service` refusals read `ignores_stream: this is an HTTP model
endpoint — …`; an endpoint that answers a streaming request with a plain
completion returns `pong` with exit 0; and a route that always answers 500
returns HTTP 502 carrying `error.message: "HTTP 500: upstream exploded"` with
`error.route`, while a successful call carries no `error` key at all.

One of those reversed a decision this project had made deliberately. A test
asserted that a gateway ignoring `stream: true` must FAIL, quoting its body, so
the reader could see an answer arriving in the wrong envelope. What the reader
got instead was a message contradicting the body beside it, a failed job and
breaker credit against a route that had answered. It now reads the answer. The
test says so, and says what it used to say.

## CLI-route pass on Linux — 2026-09-20

The gap above needed a harness CLI on Linux, and installing a real one means
putting a subscription credential inside WSL. It does not: everything listed
as unverified is harness-agnostic machinery, so a **fake harness** — a node
script registered as `harness: generic` that edits a file in its working
directory, plus a second one that prints a 429 and exits 1 — exercises all of
it with no credential and no provider call. `doctor` accepted both as ready
CLI routes and reported git available.

Driven over the real MCP stdio surface, because `workspace` diff/apply/discard
exists only there.

- **`shared`**: the edit landed in the project — `git status` showed
  `M README.md` and the new file.
- **`copy`**: `isolated: true`, `securityBoundary:
  project_state_and_process_cwd`, and the project stayed clean. `workspace
  diff` returned a real unified patch (360 bytes, README modified plus one
  file added, each with a base hash); `workspace apply` landed exactly those
  two changes in the project.
- **`git_worktree`**: a genuine second worktree, registered in the repo and
  checked out at the same commit, under the workspace base. Project untouched.
- **`discard` refused**, correctly: "2 change(s) exist only in this workspace
  and are not in your project … Discarding would destroy the only copy."
  `force: true` is what gets past it.
- **Rate-limit detection**: the throttled route recorded `calls=1 success=0
  failed=0 rate_limited=1`, breaker open with a cooldown — the 429 counted as
  a rate limit rather than a quality failure, which is the distinction
  `rate-limited-not-failed.test.ts` pins, now confirmed end to end on Linux.

The workspace machinery behaved correctly throughout. What this pass did find
sat one layer over, and only because an unapplied isolated workspace
disappeared between two observations: not retention (24 h by default), not
reproducible by replaying the sequence — WSL had shut its VM down while idle,
after which Ubuntu clears `/tmp` at boot, and `/tmp` is where the workspace
base lives by default.

**The defect that exposed was in the recovery path, and it is fixed under
`[Unreleased]`.** The missing-workspace error told the reader "the full patch
is written to the job directory at dispatch time". Measured: it was not. After
an isolated dispatch the job directory held no `workspace.patch` at all — the
patch was built only when someone called `diff` or `apply` — so the one
sentence a user saw after losing their work pointed at a file that had never
existed. `cachedPatch()`, written to read that file back, was called by
nothing.

The patch is now saved when the run finishes, and `diff`/`apply` fall back to
it. Verified on the Linux install by deleting the entire workspace tree and
then applying: the patch came back with `fromCache: true` and a note saying
the workspace is gone, and `apply` landed both changes in the project. The
error message no longer promises a patch it has not checked for.
`HARNESS_DISPATCH_WORKSPACES_DIR` on a real volume still avoids the
disappearance in the first place.

### What the dispatch log can and cannot say about routing quality

496 logged dispatches, of which 181 are test fixtures written into the real
log before test isolation was fixed (none since 2026-09-12). Of the rest:

- The router's scorer decided **146 of 496** calls; the caller named the route
  on 346. Every scored decision since 2026-08-29 carries the candidates it
  beat, so the data needed to judge it is being collected — but only **37** of
  those 57 recent decisions had more than one candidate. The other 20 compared
  nothing.
- Over those 37 real comparisons, quota refusals excluded: the router's pick
  succeeded **19/36 (53%)**, against **41/64 (64%)** when the caller named the
  route. Small n, and at least three of the scored failures are the dead-route
  defect fixed today (`local_inference` chosen over `gemini_api` twice, 0 for
  2), which is exactly why this needs re-measuring rather than concluding.
- `codex_cli` looks far worse than it is: 95 calls, 50 successes, but 24 of the
  45 non-successes are usage-limit refusals that cost nothing.
