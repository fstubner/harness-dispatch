## Suspicion sweep (2026-09-01) — reproducing the twentieth pass's read-only list

At Felix's request, and prompted by a question worth recording: "do we have
too many tests?" The measurement said no — 22.4k test lines against 21.5k
source lines, roughly 1:1 — but it also said the suite is distributed around
what has BROKEN before rather than what the product promises, which is why two
passes running found release-blockers in code that had been green for weeks.
The agreed response was not to prune or to add coverage speculatively, but to
reproduce the twentieth pass's read-only suspicions and write tests only for
the ones that turned out to be real.

Reproduced and FIXED, each sabotage-checked separately:

- **Quota counters lost under a contended lock.** `withFileLock` runs its
  critical section unlocked after a 2s timeout. That is deliberate and its
  docblock argues it well — for BreakerStore, which has nothing to fall back
  on. The argument does not transfer to QuotaCache, which keeps a pending
  delta and clears it only on success: the unserialised write lands, the delta
  is cleared as though serialised, and the real lock holder then overwrites
  the file from a baseline taken before that write. Measured against the built
  artifact: holder at 0, five calls written unlocked, holder's +3 landing last
  — final count 3, five calls gone, no error. Now `requireLock: true` for that
  caller only; the delta stays pending and lands on the next result (verified:
  final count 5). A lock miss deliberately does NOT set `persistError` —
  delayed is not undurable, and reporting it would be the same class of lie in
  the other direction.

  A second measurement worth keeping: `recordResult` persists on EVERY result,
  so while a stale lock sits there each result stalls the full 2s — five
  results measured at 10.03s total, on the dispatch return path. The stale
  steal at 10s bounds it. Not separately fixed; the deferral above is what
  makes the stall harmless rather than lossy.

- **`trip()` never counted the failure**, so `usage` showed
  `{"tripped":true,"failures":0}` for a route knocked out by a 429. Fixed with
  `lastFailureAt` set too — not scope creep: a counter with no failure time
  never decays, so incrementing without it would have been a worse bug than
  the one being fixed. An existing snapshot test asserted `failures: 0` here
  incidentally (its subject is wall-clock conversion) and was updated with a
  note saying why.

- **`discardWorkspace` left a worktree registered** when the workspace root
  was already gone: the early return skipped the removal-through-git block, so
  retention pruning or a manual delete left `.git/worktrees/<name>` in the
  user's repo forever — the outcome that function's own docblock says it
  exists to prevent. Reproduced with `git worktree list` showing the path as
  `prunable` after `discarded: true`. Prune, not remove: the directory is
  already gone.

Also added, because nothing pinned it and it is the layer-gap class that has
now bitten three times: a test that `usage`'s STATUS PAYLOAD carries the
counter-persistence warning, not merely that the cache records it. The cache
side was already pinned; the surface was not.

Probed and NOT reproduced, recorded so the next pass does not re-litigate
them from the same reading: `contextJobs` cross-project scoping — the leak is
plausible from the code, but the fixture built for it was not read back by
`buildContextPreamble` ("this job is unknown, still running, or was pruned"),
so nothing was demonstrated either way. It stays an open suspicion, not a
finding.

Still untouched from that pass's list, none reproduced: process-local breaker
state not honouring a sibling's trip, an orphaned job being uncancellable but
still claimable, `MAX_PATCH_BYTES` bounding only the worktree path, `copy` not
preserving directory modes, `.supervisors/` growing without bound, and
`apply`'s dirty-tree refusal existing only inside a git repo (that last one
was REPRODUCED by the twentieth pass and remains unfixed by choice — the
per-file hash guard still applies outside a repo, and `copy` is the documented
non-repo policy).

Suite: 1109 passed, 5 skipped, claims clean.

## Closing the open list (2026-09-01)

Every remaining item from the nineteenth and twentieth passes, at Felix's
request. Seven fixed, each reproduced first and sabotage-checked separately.
Two of the eight sabotages did not discriminate on the first attempt and are
recorded below, because that is the part worth keeping.

- **cancelJob refused every orphaned job.** The fix was initially too broad
  and an EXISTING test caught it. There are two kinds of orphaned job:
  `drainSlotQueue` WRITES the status for a slot-queued job abandoned at
  shutdown (terminal by its own error text), while `withOrphanCheck` DERIVES
  it from a stale heartbeat with the file still reading `queued` (not
  terminal — a supervisor reclaims it once the dead owner's claim ages out).
  Cancelling both was wrong; the raw file now decides. `jobs/types.ts` claimed
  "orphaned is never written to disk", which is false and is what produced the
  over-broad first attempt — corrected in place.

- **`copy` patches were unbounded in total.** The first test for this passed
  with the bound REMOVED, which is how a wrong test gets caught: a single huge
  file trips the per-file execFile maxBuffer and never reaches the
  accumulation check, so the test was proving a different fix. Rewritten with
  six 500KB files — each far under the limit, together over it — and it now
  discriminates. The per-file cap got its own test too, after ITS sabotage
  also came back green.

- **`.supervisors/` grew forever.** A killed supervisor cannot delete its
  heartbeat, so the file stopped being counted but stayed, and the liveness
  check reads every file on every drain. The sweep is deliberately limited to
  `<id>.txt`: the directory also holds `spawn-<id>.log`, which exists to
  explain a supervisor that DIED — the same one leaving the stale heartbeat.
  A sweep over every file would have deleted the diagnostic for the failure it
  was cleaning up after. Caught while writing the code, not by a test.

- **Isolated workspaces were world-readable on POSIX.** 0700 now, matching the
  state directory and every job directory; this module was the only one in the
  family with no mode at all. Applied at the roots, not to every copied
  directory — a 0700 ancestor already blocks traversal. Its test is POSIX-only
  and therefore does NOT run on this machine; the first version of it asserted
  on the run directory, which `copyTree` creates and the fix does not touch,
  so it would have pinned something untrue and failed only in CI. Retargeted
  at the directory the fix actually creates.

- **`contextJobs` had no working-directory scoping** — reproduced: a job from
  one project chained into a dispatch for another, prompt and output carried
  verbatim. DISCLOSED rather than blocked: cross-project chaining is a
  legitimate thing to want and the caller passes the id explicitly, so this is
  a missing guardrail rather than an injection route. What was actually wrong
  is that neither side could see it.

- **`workspace apply`'s description promised a refusal it cannot always make.**
  The uncommitted-changes check needs a git repository; outside one only the
  per-file hash check applies. Fixed the description rather than the
  behaviour: there is no cheap way to ask "is this dirty" without a baseline,
  and `copy` is the documented policy for non-repos.

- **The not-a-number branch still claimed routing reads `timeout_ms`.** The
  range branch beside it had been fixed for exactly this a day earlier.

Also verified in passing and NOT changed: `refreshBreakersFromStore` is called
only from the reporting path, so a sibling process's trip is not honoured
until this one finishes a dispatch of its own. Left alone deliberately — the
store IS consulted on the write path, the staleness window is one dispatch,
and making scoring re-read the file on every candidate would put a disk read
in the routing loop for a case that self-corrects.

Suite: 1120 passed, 6 skipped (the extra skip is the POSIX-only permissions
test), claims clean. Real dispatch log 425 at both ends — and per the
correction recorded above, that is evidence about the probes run outside

### The two blockers, both reproduced by the builder before fixing

- **`configure --force` silently deleted `detect: false`.** That key is the
  only thing that isolates a machine from its installed paid CLIs — this
  suite's own `setup-env.ts` depends on it — and it had no field on
  `RouterConfig`, so nothing carried it through a regenerate. Measured:
  `detect: false` + `max_concurrent_runs: 2` regenerated as the latter alone,

  requires a non-empty document. Fixed by carrying `detect` on the config
  object and emitting it — only when the file stated it, since writing the
