## Open at ship time

### Fix before the tag (recommended)

1. **Regression: in a repository with many submodules, new files silently
   drop out of a `git_worktree` patch on Windows.**
   - **Cause.** `gitlinkExclusions` (`src/workspace-resolve.ts:312`) puts
     every gitlink in the index on `git add`'s command line, as one
     `:(top,literal,exclude)<path>` pathspec each. Past Windows' command-line
     limit, Node's spawn fails with `ENAMETOOLONG`. That failure is swallowed
     by `.catch(() => undefined)` (`:210-213`). The intent-to-add step then
     never runs, so new files are missing from the patch.
   - **Measured** against dist, with gitlink paths 34 characters long
     (`third_party/vendored-library-NNNNN`):

     | Gitlinks | New file in patch? |
     |---|---|
     | 100 | yes |
     | 500 | yes |
     | 700 | **no** |
     | 2000 | **no** |

     At 700 the git command line is 39,924 characters. Spawning that git
     command directly gives `spawn ENAMETOOLONG`. The `58428e2` build, at
     2000 gitlinks, includes the new file.
   - **What the user sees.** `apply` (forced, because the fixture's project
     was dirty) reported "Applied 125 bytes". `new.js` was not in the
     project, and the message did not mention it.
   - **Why nothing is lost.** A plain `discard` afterwards refused: "1
     change(s) exist only in this workspace … (new.js (added))". Only
     `discard force: true` would destroy the file.
   - **Not a security hole.** No `git add` runs at all, so no filter runs.
   - **Suggested fix:** pass the pathspecs on stdin, with
     `--pathspec-from-file=- --pathspec-file-nul`. Or at least do not swallow
     a failed add.
   - POSIX limits are far higher. This was not measured there.

### Low

- **The CHANGELOG and the code comment overstate who can plant a junction.**
  The new junction entry says "an agent that only wrote files in its worktree
  could empty any folder". A file-writing tool cannot create a junction; that
  takes a shell or a program. Ordinary tools do create them, though: `npm`
  workspaces and `file:` dependencies do on Windows. So a well-behaved agent
  running `npm install` could also have triggered the old bug. Suggest "an
  agent that could run commands in its worktree (even `npm install`)". The
  same wording is in the comment on `removeLinksWithin` and in
  `tests/workspace-links.test.ts`.
- **The link sweep roughly doubles the cost of walking a large aged
  workspace.** Prune runs inside workspace setup, so this is time added before
  a dispatch starts.
  - **Measured** on a synthetic tree of 40,101 directories and 100,001 files,
    on this machine at about 68% CPU from other sessions:
    `removeLinksWithin` took 11,042 to 12,280 ms over 3 runs. A plain
    `readdirSync(..., {recursive: true})` of the same tree took 11,675 ms.
  - **Why it is Low.** The walk is about as fast as it can be; the cost is
    the extra pass, and git's own removal already walks the tree.
- **A workspace that cannot be checked can never be removed by
  harness-dispatch.** If `removeLinksWithin` cannot read a directory or remove
  a link, `discard` refuses and prune skips the run every time. That is the
  safe choice, and it is by design. Not tested.
- **The acceptance gate writes into the project.** Its run here wrote
  `.agent-evidence/acceptance-report.json` (gitignored; `git status` stayed
  clean).
- **Carried from the first pass:**
  - After a failed `git_worktree` setup, the `workspace` tool's message names
    the wrong policy.
  - A `copy` apply into a repo with `core.autocrlf=true` rewrote line
    endings.
  - The copy-policy `git diff --no-index` does not block a clean filter from
    user-level git config.

### Open items

1. **The Upgrading bullet on nested dispatch overstates its reach. Fix the
   wording before the tag.**
   - It says a dispatch from an agent harness-dispatch started "is refused,
     on every entry point".
   - The 0.12.0 Security entry, and r2's measurement, say otherwise. A REST
     server reads its own environment, so a delegate calling a REST server
     started normally (depth 0) is accepted. An agent with a shell can also
     unset the marker.
   - Suggested wording: "…is refused, on every kind of route, by the MCP
     tools and `harness-dispatch dispatch` (exit 1); a REST server started by
     a delegate answers 403. A REST server you started yourself does not
     check its caller."
2. **The Upgrading bullet on `.cmd` launchers is narrower than the code and
   the Fixed entries.**
   - **What the bullet says:** a prompt with `"` is refused, and a prompt
     with line breaks only on `agy.cmd`.
   - **What the code refuses** (`unsafeForCmdShim`), through any `.cmd`
     launcher:
     - any argument containing `"` or a line break (model names included)
     - a `!`, if the launcher enables delayed expansion
   - **The bullet also drops the consequence the Fixed entry states:** on
     `agy.cmd`, "any dispatch with files attached" is now refused. That is
     the case users will actually hit.
3. **A behaviour change from `0624579` is in no CHANGELOG entry or Upgrading
   bullet.**
   - **What changed.** A `git_worktree` job whose `add -A` fails now fails
     `workspace diff`/`apply` entirely.
   - **The realistic trigger:** the delegate ran `git init` in a
     subdirectory and never committed there. Before, the rest of the work
     applied (minus that directory).
   - **Assessment.** The new behaviour is the safer one, and git's message
     names the directory. But the error carries no guidance: removing
     `emb/.git` in the worktree, or committing inside it, is the way forward.
     `discard` without `force` still refuses, so nothing is lost.
   - **Suggestion:** one CHANGELOG line, and ideally a hint in the error.
4. **The forced add of gitignored files still swallows failure. Pre-existing,
   measured on both builds.**
   - **What happens.** `add -N --force` over the batch of recorded changes
     still has `.catch(() => undefined)` (`workspace-resolve.ts:239`).
   - **Measured.** The delegate created an embedded repo with a commit
     (`emb/e.txt`) and also wrote a gitignored `plain.env`. The batch failed
     with "fatal: Pathspec 'emb/e.txt' is in submodule 'emb'". `plain.env`
     was silently left out of the patch, and `apply` reported "Applied 425
     bytes". This was identical on `239b753` and `0624579`.
   - **How much can drop.** Up to 100 gitignored files per batch.
   - **How to fix.** Leave paths under a gitlink out of the candidates, or
     stop swallowing this failure too.
   - **The commit message is accurate as worded.** It says only "a failed
     add -A".
5. **A tampered record can still name a sibling run directory. Residual, same
   class as before.**
   - **Measured.** A record whose `workspaceRoot` is another job's run
     directory was discarded without `force`, together with that job's
     unapplied file. The tampered record's own `changedFiles: []` skips the
     unapplied-work check.
   - **Why it is residual.** Nothing binds a run directory to a jobId, and
     whoever can write job records can delete files directly. The fix chose
     a "holds runs" test rather than r2's suggested run-directory-shape
     check, and it closes the measured project-level case.
6. **The 1500-gitlink regression test only bites on Windows.** Its exclusion
