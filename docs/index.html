Route coding tasks to the agent that fits.

harness-dispatch turns the coding harnesses already on your machine (Claude Code, Codex, Cursor, Antigravity) and any local or remote OpenAI-compatible endpoint into tools any AI can call, and handles the async nature of long-running work.

01 — How it works

Not every task wants the same agent.

Codex is good at grinding through execution with its own test loop. Claude tends to plan and architect better. Cursor has editor-aware context built in. harness-dispatch matches the task to whichever fits, then hands off to that agent's own CLI. No proxy in between.

Task type

Execute, plan, review — each has a different best-fit agent.

Billing policy

Metered or unknown-billing routes are blocked until you opt in.

Live quota

Routes with available quota are preferred; rate-limited ones are skipped.

Safety profile

read_only, workspace_edit, full_auto gate what an agent can touch.

02 — Setup

Configure is the entrypoint.

One command finds what's installed, checks it actually works, and writes the config for you.

  1. Detect Claude Code, Codex, Cursor, Antigravity, and configured endpoints.
  2. Verify availability and auth without spending quota where possible.
  3. Choose billing policy, safety profile, and workspace policy per route.
  4. Write config, print an MCP snippet, connect your agent.
mcp config
{
  "mcpServers": {
    "harness-dispatch": { "command": "harness-dispatch" }
  }
}

04 — FAQ

Short answers.

Why local only?

Nothing phones home. Traces (if enabled) go to localhost unless you point them elsewhere. The one outbound call is a public leaderboard GET for route scoring.

Why require opt-in for paid routes?

Routes with no provider-side backstop — a raw metered API key, or unknown billing — stay blocked until you set allow_paid_usage: true on it. Subscription overage on the provider's own side (Cursor on-demand billing, Claude usage credits, Codex flexible credits) isn't something harness-dispatch can detect or block — if your account has that enabled, it applies exactly as it would outside this tool.

How is this different from a model proxy?

Proxies swap which model answers your agent's next request. harness-dispatch swaps which agent runs the task; each harness keeps its own scaffolding, tools, and context.

Why explicit tools instead of prompt instructions?

Models are trained on tool calling. An agent given a code or job tool reliably delegates; a prompt telling it to shell out to another CLI often gets ignored.

Is it production-ready?

The high-stakes paths are tested against real behavior rather than mocks: billing gating for every billing kind, workspace isolation actually dispatching away from your source tree, and subprocess timeouts and cleanup against real spawned processes. CI runs on Windows, macOS, and Linux.
